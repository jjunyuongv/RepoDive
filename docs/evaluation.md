# RepoDive 평가

검색 정확도, 답변의 인용 정확도, 거절 정확도, 행 번호 정확도를 어떻게 재고 무슨 결과가 나왔는지
정리합니다. 수치는 전부 `Back/logs/`에 남은 기록과 그것을 다시 읽어 낸 값이고, 이 문서를 위해 새로
잰 것은 없습니다. 동작 설명은 [architecture.md](architecture.md)에 있습니다.

## 1. 원칙

- **기준을 측정 전에 정합니다.** 결과를 보고 기준을 정하면 측정이 아니라 사후 합리화가 됩니다. tool use
  도입 판정 기준은 테스트 파일 docstring에 측정 전에 적어 두었습니다.
- **무과금으로 잴 수 있는 것은 무과금으로 잽니다.** 검색 지표는 로컬 임베딩만 쓰고, 행 번호 정확도와 거절
  재채점은 저장된 답변 원문을 다시 읽습니다. LLM을 부르는 측정은 `billed` 마커를 따로 달아 실수로 돌지 않게
  합니다.
- **답변 원문을 남깁니다.** 채점기를 고쳐야 할 때 LLM을 다시 부르지 않고 재채점할 수 있습니다. 실제로 두 번
  그렇게 했습니다.
- **채점은 문자열 매칭입니다.** LLM 심판을 쓰지 않아 결정적이고 무과금이지만, "규정 문구를 안 썼을 뿐인 옳은
  답"을 실패로 셉니다. 두 방식을 비교하는 데는 쓸 수 있지만 절대값을 품질로 읽으면 안 됩니다.

## 2. 평가셋

`Back/tests/search_eval_dataset.py` 한 파일에 있습니다. 저장소 이름이 코드에 들어가는 곳은 여기뿐입니다.

| 세트 | 저장소 | 성격 | 소스 번들 토큰 | 한국어 질의 | 식별자 질의 | 거절 질의 |
|---|---|---|---|---|---|---|
| air | `jjunyuongv/air` | Java 웹앱 (Spring Boot) | 62,380 | 12 | 5 | 6 |
| marryday | `jjunyuongv/marryday` | Python/JS 웹앱 (FastAPI + React) | 1,057,764 | 10 | 6 | 6 |
| apns4j | `teaey/apns4j` | Java 라이브러리 | 34,467 | 10 | 6 | 6 |

- **한국어 개념어** ("비밀번호는 어떻게 암호화해?"). 코드에 그 단어가 없을 수 있습니다. 검색 개선의 주 대상입니다.
- **영문 식별자** ("PasswordEncoder"). 코드에 실제로 있는 이름이라 이미 잘 되는 편이고 회귀 감시용입니다.
- **거절 질의.** 저장소에 없는 기능을 묻습니다. 정답이 없으므로 순위 지표를 잴 수 없고, 답변이 규정대로
  거절했는지만 봅니다. 정답 질의와 섞지 않습니다. 섞으면 Recall@8의 분모가 바뀌어 기존 기록과 비교가 끊기고
  인용 정확도가 조용히 희석됩니다.

**정답 표기**는 청크 id가 아니라 `(파일 접미사 + 포함 문자열)`입니다. 청킹 규칙을 바꾸면 청크 경계가 달라져
id 기반 정답은 전부 무효가 됩니다. 한 질의에 정답을 여럿 둘 수 있고, `must_not_contain`으로 import 줄이나
모듈 docstring이 정답으로 인정되는 것을 막습니다.

**질의를 지어내지 않았습니다.** 저장소 소스를 먼저 읽고 정답이 실제로 있는 것만 골랐습니다. 거절 질의도
낱말 검색 0회만으로 부재를 판정하지 않고 기능 이름, 그 기능이 쓰는 식별자·상수, 주소·포트를 함께 확인한 뒤
근거를 남겼습니다. `http2`가 0회라 "HTTP/2 전송이 없다"고 적었는데 `api.push.apple.com:443` 상수가 있었던
반례에서 나온 규칙입니다.

**v2에서 판정을 조였습니다.** v1은 정답 조건이 헐거워 정답 파일의 청크 대부분이 정답으로 인정된 질의가
있었습니다(2개 질의가 100%). 그러면 "그 파일 어딘가만 걸리면 통과"라 청크 단위 개선이 지표에 안 잡힙니다.
조인 뒤 그 질의들의 정답 비율은 25%, 50%가 됐고, 질의와 정답이 어긋난 2건도 고쳤습니다. v1과 v2는 비교하지
않으며 버전이 기록에 함께 남습니다.

## 3. 지표와 실행 방법

| 지표 | 무엇을 재나 | 파일 | 과금 |
|---|---|---|---|
| Recall@8, MRR, 평균 순위 | 검색 상위 8개 안에 정답 청크가 있는가. 순위를 알기 위해 전체 순위를 뽑음 | `test_search_quality.py` | 없음 |
| 인용 정확도 | 답변 텍스트에 정답 파일명이 있는가 | `test_citation_quality.py` | 있음 |
| 거절 정확도 | 거절 질의 답변의 첫 문장이 "[어디를 봤는가] + [거기에 없다]" 구조인가 | `test_citation_quality.py`, `test_rescore_refusals.py` | 있음 / 재채점은 없음 |
| 질문당 비용 | 토큰 기록으로 계산한 실비. 기준선 대비 배수 | `test_citation_quality.py` | 있음 |
| 행 번호 정확도 | 답변이 인용한 코드 조각이 소스의 그 행 범위 안에 실제로 있는가 | `test_line_accuracy.py` | 없음 |

```bash
cd Back
pytest -m evaluation tests/test_search_quality.py -s                   # 검색 지표
pytest -m evaluation tests/test_line_accuracy.py -s                    # 행 번호 정확도
pytest -m evaluation tests/test_rescore_refusals.py -s                 # 거절 무과금 재채점
pytest -m "billed and evaluation" tests/test_citation_quality.py -s    # 인용 · 거절 · 비용 (과금)
```

`evaluation`과 `billed` 마커는 `-m`에 명시한 것만 돕니다. 기본 `pytest`에서는 빠지고, `-m billed`만 쓰면
`evaluation` 마커가 없어 조용히 전부 skip 됩니다. 검색 결과는 `logs/search_evals.jsonl`에 (모델, 테이블,
저장소, 평가셋 버전) 키로 쌓여 관리자 페이지에서 비교하고, 답변 품질 결과는 `logs/citation_evals.jsonl`에
답변 원문과 도구 호출 내역까지 남습니다.

인용 정확도에 순위 지표를 쓰지 않는 이유는 전체 주입에는 검색이 없기 때문입니다. 형식상 Recall@∞ = 1.0이
되어 자동으로 만점이 됩니다. 대신 답변이 정답 파일을 실제로 짚었는지를 셉니다.

## 4. 검색 정확도

### 임베딩 모델 교체

"PasswordEncoder 어디서 만들어?"는 1위인데 "비밀번호는 어떻게 암호화해?"는 17위였습니다. 원인은 모델이었습니다.
`jina-embeddings-v2-base-code`의 "multilingual"은 프로그래밍 언어 30종을 뜻하고 자연어는 영어만 지원합니다.
같은 청킹, 같은 평가셋(air 17개)에서 모델만 바꾼 결과입니다.

| 구분 | jina-code (768) | multilingual-e5-large (1024) |
|---|---|---|
| 한국어 Recall@8 | 0.17 (2/12) | 0.67 (8/12) |
| 한국어 MRR | 0.0665 | 0.4909 |
| 한국어 평균 순위 | 67.92 | 12.83 |
| 식별자 Recall@8 | 0.80 | 0.80 |
| 임베딩 시간 (145청크) | 38.4초 | 73.2초 |
| 모델 크기 | 655MB | 2,149MB |
| 512 토큰 한도에 잘린 청크 | 0 | 15 (10.3%) |

한국어 12개가 전부 좋아졌고 나빠진 것은 식별자 1개(1위→2위)였습니다. E5는 `query: `/`passage: ` 접두어가
필수인데 fastembed가 붙여 주지 않아 직접 붙이고 테스트로 고정했습니다.

### 청킹 수정

모델을 바꾸자 잘리는 청크와 함께 청킹 결함이 드러났습니다. 세 결함을 한 번에 고치지 않고 단계마다 잤습니다.
한꺼번에 고쳤다면 앞 두 단계가 한국어를 깎아 먹은 것을 알아채지 못했을 것입니다.

| 지표 (air) | 수정 전 | 2a 헤더 복구 | 2b 800자 재분할 | 2c 저정보 감점 |
|---|---|---|---|---|
| 잘린 청크 | 15 | 14 | 0 | 0 |
| 식별자 Recall@8 | 0.80 | 1.00 | 1.00 | 1.00 |
| 한국어 Recall@8 | 0.67 | 0.58 | 0.50 | 0.67 |
| 한국어 MRR | 0.4909 | 0.4573 | 0.4122 | 0.5028 |
| 전체 Recall@8 | 0.71 | 0.71 | 0.65 | 0.76 |

- **2a.** 클래스 헤더가 200자 미만이라 통째로 버려져 한 질의의 정답이 색인에 없었습니다. 순위 문제가 아니라
  부재였습니다.
- **2b.** 청크 목표 2,400자 → 800자. e5-large 한도 512 토큰과 문자/토큰 비율 최악 1.60(한국어 주석)에서
  역산했습니다. 잘린 14개 중 10개가 CSS였습니다.
- **2c.** 스타일시트와 선언만 있는 조각에 0.03 감점. CSS는 한국어 주석이 많아 한국어 질의와 곧잘 맞았고, 2b에서
  잘게 쪼개지며 오히려 더 잘 맞게 됐습니다. 감점 값은 0.03부터 회복되고 0.05 이상은 변화가 없어(사실상 제외가
  되는 구간) 포화 직전에서 멈췄습니다. 상속·구현 선언은 감점에서 제외합니다. 2a에서 살린 헤더가 바로 그것입니다.

같은 수정을 Python/JS 저장소(marryday)에서 확인했을 때 한국어 Recall@8은 0.80이었습니다. 반대로 청크를
2,400자로 되돌리는 안은 이 저장소에서 한국어 Recall@8을 0.60으로 떨어뜨려(임베딩 시간은 96분 → 39분)
채택하지 않았습니다. 정답이 큰 덩어리에 섞이면 초점이 흐려집니다.

### int8 양자화

색인 시간을 줄이려고 같은 모델의 int8 ONNX를 잤습니다. 크기 2,132MB → 536MB, 속도 2.52배(인터리브 3라운드
중앙값 409 → 162 ms/청크), fp32 벡터와의 코사인 0.993~0.995.

| 저장소 | 한국어 Recall@8 fp32 → int8 | 식별자 Recall@8 | 전체 Recall@8 |
|---|---|---|---|
| air | 0.67 → 0.75 | 1.00 → 1.00 | 0.76 → 0.82 |
| marryday | 0.80 → 0.80 | 0.83 → 0.83 | 0.81 → 0.81 |
| apns4j | 0.50 → 0.60 | 1.00 → 1.00 | 0.69 → 0.75 |

채택 기준은 "저장소별 한국어 Recall@8 동률 이상"이었고 셋 다 충족했습니다. "올랐다"보다 "떨어지지 않았다"로
읽는 것이 맞습니다. 개별 순위는 요동쳤고 표본 38개에서 경계에 있던 것이 우연히 유리하게 뒤집혔을 수 있습니다.
양자화가 검색을 좋게 만들 이유는 없습니다.

## 5. 답변 품질 — tool use 도입 판정

작은 저장소는 소스 전체를 프롬프트에 넣고(전체 주입), 큰 저장소는 검색 결과를 미리 넣는 방식(RAG)과 모델이
도구를 직접 부르는 방식(tool use) 중 어느 쪽이 나은지 같은 실행에서 나란히 잤습니다. 팔은 저장소 이름이 아니라
소스 번들 토큰으로 갈립니다. 57,000 토큰 이하일 때만 전체 주입 팔이 붙고, 프로덕션이 판정에 쓰는 함수를 그대로
씁니다.

### 판정 기준 (측정 전에 고정)

```
A. 인용 정확도가 기준선보다 떨어지면 기각.
B. A가 동률이면 거절 정확도를 본다. 떨어지면 기각.
C. A·거절이 올라도 질문당 비용이 기준선의 3.0배를 넘으면 전면 도입하지 않고 큰 저장소 전용으로만 켠다.
```

거절 축이 따로 필요한 이유는 인용 정확도가 정답이 있는 질의에서만 재기 때문입니다. 정답이 없는 질의에서는
짚을 파일이 없어 날조와 침묵이 똑같이 0점으로 보입니다. 검색을 반복하는 경로는 계속 뒤지다 지어낼 여지가 더
크므로 그것을 재려면 거절 질의가 있어야 합니다.

### 결과

156 호출, 26분 42초, 실비 $2.1259. 거절 정확도는 채점기 수정 후 재채점한 값입니다(6절).

| 세트 | 팔 | 인용 정확도 | 거절 정확도 | 질문당 비용 | 질문당 지연 | RAG 대비 비용 |
|---|---|---|---|---|---|---|
| air | rag | 0.7647 | 1.0 | $0.009141 | 6,068ms | 1.00배 |
| air | tool | **1.0** | 1.0 | $0.016109 | 10,909ms | **1.76배** |
| marryday | rag | 0.6875 | 0.8333 | $0.010835 | 6,886ms | 1.00배 |
| marryday | tool | 0.75 | 1.0 | $0.021569 | 12,609ms | 1.99배 |
| apns4j | rag | 0.8125 | 1.0 | $0.008392 | 5,980ms | 1.00배 |
| apns4j | full | **1.0** | 1.0 | $0.015939 | 6,671ms | 1.90배 |
| apns4j | tool | 0.9375 | 0.6667 | $0.013505 | 9,762ms | 1.61배 |

**판정: 임계값을 넘는 저장소는 tool use, 이하는 전체 주입.**

- **air가 근거입니다.** 인용 0.7647 → 1.0(+0.235). 질의가 17개라 한 건이 0.0588이므로 4건분이고, 프롬프트
  변경이 기준선을 움직인 폭(+0.06, 한 건)과 크기가 명확히 갈립니다. A 통과, B 동률, C는 상한의 절반 아래입니다.
- **marryday는 독립 근거가 아닙니다.** +0.0625는 정확히 한 건이라 노이즈와 구분되지 않습니다. 판정을 뒤집지
  않은 것이지 받친 것이 아닙니다. air와 같은 코드 경로이므로 세트별로 켜고 끄지 않습니다.
- **apns4j는 기각입니다.** 전체 주입 1.0 > 도구 0.9375. 기준 A는 "떨어지면 기각"이므로 임계값 이하 저장소에는
  도구를 켜지 않습니다. apns4j/tool의 거절 0.6667은 원문을 읽어 확인한 결과 날조 0건이었고, 양보("옵션은
  있지만 … 발견되지 않았습니다")와 동일성 부정("…에 대한 것이지 …아닙니다")을 채점기가 의도대로 거절로
  치지 않은 것입니다.

**표본의 한계.** 이 판정이 기대는 독립 근거는 사실상 한 세트입니다. 표본을 늘리려면 임계값을 넘는 저장소를
평가셋에 더해야 합니다.

**상한은 병목이 아니었습니다.** 왕복 상한 3회에 걸린 질의의 인용 정확도가 19/21로, 안 걸린 쪽(1회 12/12,
2회 13/16)보다 낮지 않았습니다. 결과 절단 800 토큰도 마찬가지입니다. 도구 호출은 세 세트 합계
`grep 86 · search_code 83 · read_file 52`였습니다.

**비용.** 도구 상한 셋(왕복 3회, 결과 800 토큰, grep 30줄)은 이 기준 C에서 역산한 값입니다. 검색 결과 사전
주입과 도구를 함께 쓰는 하이브리드는 스니펫이 캐시 지점 뒤에 있어 왕복마다 재청구되어 3회에 3.78배로 기준을
넘었고, 순수 도구는 2.11배였습니다. 하네스의 캐시 접두사(약 1,140 토큰)는 프로덕션(8,120 토큰)의 1/7이라
판정(상대 배수)에는 영향이 없지만 절대 비용을 예산 값으로 쓰면 실제보다 헐거워집니다.

## 6. 거절 정확도

프롬프트는 근거가 없을 때 쓸 문구 둘("주어진 정보로는 알 수 없습니다", "검색된 범위에는 없습니다")을 정합니다.
채점기는 두 번 샜습니다. 처음은 문구의 연속 문자열 매칭이었는데 모델이 "검색된 `코드` 범위에는 없습니다"처럼
낱말을 끼워 넣어 24건 중 15건을 놓쳤고, 다음은 부정 술어를 낱말로 나열했는데 `발견되지 않`, `없고`,
`소스 전체`(패턴은 `전체 소스`) 같은 변형으로 15건을 놓쳤습니다.

**두 번 다 날조는 0건이었습니다.** 실패 30건을 전부 읽었고 모두 모델이 "없다"고 정확히 답했습니다. 문제는
답변이 아니라 자였고, 저장된 원문으로 API 호출 0회에 재채점했습니다.

지금 채점기는 낱말이 아니라 문장 구조로 봅니다. 스코프 표현 6종(`전체 X` / `X 전체` 양쪽 어순)과 부정 3종
(`없-`+어미, `[탐색 동사]+지 않`, 가능성 부정)이 첫 문장에 이 순서로 나오는지 보고, 양보는 거절로 치지
않습니다. 첫 문장만 보는 이유는 프롬프트가 "한 문장으로 밝히라"고 하므로 진짜 거절은 답변을 열면서 나오고,
본문 어디든 보면 근거를 댄 뒤의 단서까지 거절로 잡히기 때문입니다. `test_rescore_refusals.py`가 양쪽에서
조입니다. 거절 질의 답변은 전부 잡히고, 정답을 짚은 답변은 하나도 거절로 잡히지 않습니다.

## 7. 인용 정확도 — 파일과 행 번호

### 인용 파서

답변에서 `(파일, 행 범위)`를 뽑는 파서는 화면 링크와 행 번호 채점이 같은 함수를 씁니다. 저장된 답변 8기록에
옛 파서와 새 파서를 각각 돌려 건별로 대조했습니다. LLM 호출 0회.

| | 수정 전 | 수정 후 |
|---|---|---|
| 인용 추출 | 535 | 814 |
| 행 표기를 잡고도 버림 | 358 | 79 |
| 그중 경로 해석 실패 | 171 | 0 |
| 새로 생긴 잘못된 링크 / 전에 맞던 것이 틀리게 된 건 | | 0 / 0 |

경로 해석 실패 171건은 전부 파일이 아닌 문자열이었습니다. 라우트(`/login`), 주석, 산술식, 점 표기(`np.isin`),
URL이 파일명 자리에 들어앉았고 실제 파일은 0건이었습니다. 수정은 셋입니다. 파일명 후보를 수집되는 소스
확장자로 끝나는 것으로 조였고(보관되는 파일은 그 확장자뿐이라 잃는 링크가 없음), 파일명은 보관 경로 목록으로
실제로 풀리는 것을 우선해 고르고, 접미사 매칭을 `/` 경계에서 끊었습니다. 경계를 안 끊으면
`ApnsPayload.java`가 `Payload.java`에 맞아 답변이 파일을 정확히 적어도 버려졌습니다(7건).

Java 클래스명을 파일로 매핑하는 안은 관례가 72/72로 확실했지만 실제 답변에서 틀린 링크가 나와 하지
않았습니다. 한 줄에 유일하게 매핑되는 심볼이 `ChatHandler`인데 그 줄이 말하는 파일은 `ChatSocketConfig.java`
였습니다. 내용이 그럴듯해서 더 알아채기 어렵습니다.

### 행 번호 정확도

답변이 코드 조각과 행 번호를 함께 말했을 때 그 조각이 소스의 그 범위 안에 실제로 있는지 봅니다. 코드를 그대로
인용한 것(공백·구두점·괄호가 있는 조각)만 채점하고, 이름 하나만 적은 것은 서술이라 뺍니다. 같은 조각이
여러 곳에 있으면 하나라도 범위에 들면 맞다고 봅니다. 그래서 이 수치는 정확도의 하한이 아니라 대략적 빈도입니다.

| 시점 | 정확도 | 비고 |
|---|---|---|
| 첫 측정 | 50% (15/30) | RAG 62%, 전체 주입 45% |
| 프롬프트 수정 후 | 75% (21/28) | RAG 69%, 전체 주입 80% |
| 인용 파서 수정 후 (현재) | 71.1% (165/232) | 판정불가 104, 틀림 67 |

원인이 경로마다 달랐습니다. RAG의 오차는 +3, +4, +22처럼 작고 양수였습니다. 스니펫에 줄 번호가 없어 모델이
직접 세다 어긋난 것입니다. 전체 주입의 오차는 -110 ~ +112로 양방향이고 컸습니다. 큰 소스 안에서 같은 이름의
다른 위치를 짚은 것입니다.

스니펫에 줄 번호를 붙이는 안은 청크가 원본과 줄 수부터 어긋나는 경우가 48.8%라 되돌렸습니다. 대신 프롬프트를
사실에 맞게 고쳤습니다. 줄 번호가 붙어 온 코드는 그대로 읽고, 검색 조각은 헤더의 범위만 인용하고, 확실하지
않으면 행 번호 없이 이름으로만. 전체 주입 경로는 인덱스를 쓰지 않으므로 45% → 80%가 프롬프트 효과의 순수한
증거입니다. 분모가 30 → 28로 줄어든 것도 함께 봐야 하지만 정확한 건수 자체가 15 → 21로 늘었으므로 "덜 말해서
정확해진 것"만은 아닙니다.

서버는 이 수치를 고쳐 주지 않고 그대로 넘기며, 화면이 인용 범위 앞뒤 20행을 함께 보여 줍니다. 틀린 것을
감추면 고칠 수가 없습니다.

개선 전후를 한 표로 모은 요약은 README의 "핵심 성과" 절에 있습니다.

## 8. 한계

- tool use 판정의 독립 근거가 한 세트입니다.
- 거절 채점기는 화이트리스트라 답변 양식이 바뀌면 다시 샐 수 있습니다. 답변 원문을 남겨 무과금 재채점으로
  대응합니다.
- 행 번호 정확도는 코드를 그대로 인용한 것만 채점하므로 대략적 빈도입니다.
- 인용 정확도는 파일을 짚었는지를, 거절 채점기는 첫 문장을 봅니다. "맞는 인용을 다음 턴에서 철회하는" 경우를
  재는 자는 없습니다. 실제로 행 번호가 전부 맞는 인용을 모델이 추궁성 질문에 "추정으로 만들어낸 값"이라고
  철회한 표본이 있고, 원인은 도구 결과를 이력에 남기지 않아 다음 턴의 모델이 앞 답변의 출처를 못 보는 구조입니다.
- 비용 기준선 표본은 전부 개발자 본인의 검수 트래픽입니다. 외부 사용자 트래픽이 생긴 뒤 다시 뽑아야 합니다.
