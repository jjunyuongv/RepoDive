# RepoDive 아키텍처

RepoDive가 지금 어떻게 동작하는지, 왜 그렇게 정했는지, 어디까지가 한계인지를 적습니다.
코드와 이 문서가 다르면 코드가 맞습니다. 평가 방법과 수치는 [evaluation.md](evaluation.md)에 있습니다.

설계 원칙은 둘입니다. 싼 검사를 먼저 하고 비싼 호출(GitHub, LLM)을 마지막에 합니다. 오래 걸리는
일(코드 색인)은 사용자를 기다리게 하지 않습니다.

## 1. 구성

```
브라우저 ── nginx :80 ─┬─ /                          정적 파일 (React · Vite)
                       └─ /analyze /chat /auth /health ──→ FastAPI :8000 ──→ PostgreSQL 17 + pgvector

FastAPI 프로세스 안
  ├─ 요청 스레드          /analyze · /chat 처리, Claude 호출
  ├─ 색인 워커 스레드 1개  큐에서 꺼내 청킹 → 임베딩 → pgvector 저장
  └─ 임베딩 모델 (ONNX)   로컬 실행, 과금 없음. 기동 시 별도 스레드로 미리 올림
```

관리자 페이지 `/admin`은 인증이 없어서 nginx가 프록시하지 않습니다. 컨테이너 네트워크 안에서만 닿습니다.
DB는 선택입니다. 없으면 요약 캐시가 꺼지고 대화 기능이 503을 냅니다.

## 2. 요청 흐름

### `POST /analyze` — 저장소 주소에서 요약까지

| 순서 | 동작 | 비용 |
|---|---|---|
| 1 | URL 파싱, 허용 목록 검사(로그인하지 않은 요청만) | 0 |
| 2 | 접근 확인. 비공개·삭제·빈 저장소를 걸러냄 | GitHub 1회 |
| 3 | 요약 캐시 조회. 히트면 색인 시작만 시도하고 바로 응답 | DB 1회, LLM 0회 |
| 4 | 남용 제한 검사 | 0 |
| 5 | README, 매니페스트, 파일 목록 수집 | GitHub 3회 이상 |
| 6 | tarball로 소스 수집 후 정적분석 | GitHub 1회 |
| 7 | Claude 요약 생성 | LLM 1회 |
| 8 | 스냅샷 저장(요약 + 컨텍스트 원문), 6의 소스와 함께 색인을 큐에 넣고 기다리지 않음 | DB |

순서가 이렇게 된 이유는 앞 단계가 뒤 단계의 비용을 막기 때문입니다. 허용 목록이 접근 확인보다 앞인
것은 차단할 요청에 GitHub 호출을 쓰지 않으려는 것이고, 캐시 조회가 남용 제한보다 앞인 것은 LLM 비용이
없는 요청까지 한도를 깎을 이유가 없어서입니다. 정적분석이 요약보다 앞인 것은 요약이 코드 상태를 말하려면
결과가 먼저 있어야 해서입니다.

요약 캐시 키는 `{owner/repo 소문자}@pushed_at:{타임스탬프}`입니다. 커밋 SHA가 아니라 `pushed_at`인
이유는 접근 확인 응답에 이미 들어 있어 추가 요청이 없기 때문입니다.

**수집 범위.** 소스 파일은 확장자가 지원 목록(39개)에 있고, 200KB 이하이고, `node_modules` 같은 디렉터리
밖에 있고, 전체 3,000개 이내인 것만 꺼냅니다. 색인, 도구, 인용이 보는 파일 집합이 전부 이것입니다.
그래서 "저장소에 없다"와 "수집 범위에 없다"는 다른 말이고, 프롬프트도 모델에게 그 둘을 구분하라고 합니다.

**정적분석.** ruff(`E9,F`), oxlint(`correctness`), PMD(`errorprone`), stylelint(결함성 규칙 14개)를
설정 파일을 읽지 않는 모드로 돌려 집계만 요약 프롬프트에 넣습니다. ESLint처럼 저장소의 설정 파일(=JS 코드)을
실행하거나 `npm install`이 필요한 도구는 남의 코드를 우리 서버에서 실행하는 경로가 되어 쓰지 않습니다.
규칙을 고정하는 것은 도구 버전이 오를 때 요약이 조용히 바뀌지 않게 하려는 것이고, 의견성 규칙을 빼는 것은
오탐을 "결함"이라 적으면 틀린 말이 되기 때문입니다.

### 코드 색인 — 백그라운드

```
소스 확보 → 소스 원문을 스냅샷 단위로 보관 (snapshot_source_files)
   ▼
작은 저장소인가?  바이트 ≤ 500KB 이고 Claude 토큰 계산 ≤ 57,000 토큰
   예 → 줄 번호를 붙인 소스 번들을 스냅샷에 저장, 청크 0개로 완료      (전체 주입)
   ▼ 아니오
tree-sitter 청킹 → 청크 수 > 300 이면 skipped 로 닫음 (임베딩 없음)
   ▼
로컬 임베딩 → pgvector 저장 → 완료 표시와 활성 포인터 교체 (한 트랜잭션)
```

큐 하나에 워커 하나입니다. 임베딩이 CPU를 전부 쓰기 때문에 여러 색인이 겹치면 어느 것도 끝나지 않습니다.
진행 상태는 DB에 남기고 화면이 "N/M개, 약 X분 남음"을 폴링합니다.

### `POST /chat` — 질문에서 답변까지

세션을 읽고 남용 제한을 건 뒤, 스냅샷 상태에 따라 세 갈래로 답합니다.

| 스냅샷 상태 | 하는 일 |
|---|---|
| 소스 번들이 있다 (전체 주입) | 번들을 캐시가 걸리는 첫 사용자 메시지에 넣고 도구 없이 답한다 |
| 색인 완료 | `search_code`, `read_file`, `grep` 도구를 붙여 모델이 직접 부르게 한다 |
| 색인 중, 실패, skipped | 도구 없이 요약과 파일 목록만으로 답한다. 화면이 상태 배너를 띄운다 |

답변이 오면 질문·답변을 한 트랜잭션으로 저장하고, 답변에서 인용을 뽑아 보관 소스 경로로 연결해 돌려줍니다.

## 3. 저장소 크기에 따른 분리

판정은 저장소 이름이 아니라 크기로만 합니다. 프로덕션 코드에 저장소 이름을 쓰지 않는 것이 규칙이고,
분기는 언어, 청크 수, 파일 크기 같은 속성으로만 합니다.

**전체 주입 (57,000 토큰 이하).** 소스 전체를 `12|코드` 형식으로 줄 번호를 붙여 프롬프트에 넣습니다.
검색을 만들지 않고 도구도 붙이지 않습니다. 소스가 이미 접두사에 다 들어가 있어 검색해 봐야 그 일부를
두 번 보내는 셈이기 때문입니다. 판정에 바이트를 먼저 보는 것은 명백히 큰 저장소를 싸게 거르기 위해서고,
통과 판정은 Claude 토큰 계산 API(추론을 돌리지 않아 무과금)로 실제 토큰 수를 셉니다. 바이트 추정이
저장소에 따라 24~32% 어긋났기 때문입니다. 임계값은 캐시 배율과 세션당 질문 수에서 역산한 값입니다.

**Tool use (57,000 토큰 초과).** 모델이 필요할 때 도구를 부릅니다. 검색 결과를 미리 넣지 않습니다.

| 도구 | 하는 일 | 상한 |
|---|---|---|
| `search_code` | 질문을 임베딩해 의미가 가까운 코드 조각 8개. 경로와 행 범위를 헤더로 | 결과 800 토큰 |
| `read_file` | 보관 소스에서 지정한 줄 범위를 실제 줄 번호를 붙여 읽음. 범위 인자 필수 | 결과 800 토큰 |
| `grep` | 보관 소스 전체에서 부분 문자열이 든 줄 | 30줄 |

왕복 상한은 3회입니다. 상한 셋은 비용 산식에서 나왔습니다. 왕복 R회의 입력은 앞 왕복의 결과가 계속
누적되어 꼬리가 이차로 커지는데, 결과 800 토큰일 때 R=3이 기준선의 2.51배, R=4가 3.66배로 판정 기준
3배를 넘습니다. 한도에 닿으면 `tool_choice`를 바꾸지 않고 마지막 메시지 꼬리에 "지금까지 얻은 근거로
답하라"는 안내만 붙입니다. `tool_choice` 변경은 messages 캐시를 무효화합니다.

`read_file`에 범위 인자가 필수인 것은 편의가 아니라 비용 장치입니다. 선택으로 두면 모델이 파일을 통째로
부르고 그 결과가 왕복마다 누적됩니다. 결과가 잘리면 잘렸다는 사실을 결과 안에 적습니다. 적지 않으면 모델이
잘린 것을 "없다"로 읽습니다.

**두 방식을 크기로 가른 근거는 측정입니다.** 임계값을 넘는 저장소에서 도구 방식의 인용 정확도가 0.7647 →
1.0이었고, 임계값 이하 저장소에서는 전체 주입 1.0 > 도구 0.9375로 반대였습니다. 세부는 evaluation.md 5절.

**세 번째 상태.** 청크 수가 300개를 넘으면 임베딩을 하지 않고 `skipped`로 닫습니다. 요약과 파일 목록으로는
답하되 코드 검색과 도구만 없는 상태입니다. `failed`와 나눈 이유는 재시도 때문입니다. 종료 상태를 구분하지
않으면 질문마다 새 빌드를 만들어 tarball을 다시 받습니다. 판정은 청킹을 마친 뒤 실제 청크 수로 합니다.
청킹은 236청크에 0.76초라 상한이 지키는 시간의 2%도 안 되고, 바이트로 추정하면 언어에 따라 1.64배
벌어집니다.

## 4. 코드 검색

```
소스 → tree-sitter로 함수·클래스 경계에서 자름 (목표 800자, 200자 미만은 이웃과 합침)
     → 로컬 ONNX 임베딩 (multilingual-e5-large int8, 1024차원, passage: 접두어)
     → pgvector (HNSW)

질문 → 같은 모델로 임베딩 (query: 접두어)
     → 활성 빌드 안에서 코사인 거리 상위 40개 (8 × 5) 후보
     → 스타일시트·선언만 있는 조각에 0.03 감점 후 다시 정렬
     → 상위 8개
```

- **tree-sitter로 자르는 이유.** 줄 수로 자르면 함수 한가운데가 끊깁니다. 파서가 없거나 파싱이 깨진 파일은
  줄 기준으로 자릅니다. 클래스는 크기가 작아도 항상 내부 메서드로 내려갑니다. 클래스를 통째로 한 청크로
  두면 그 벡터가 모든 일의 평균이 됩니다.
- **800자인 이유.** 2,400자로 넉넉히 잡으면 Python/JS 저장소에서 한국어 Recall@8이 0.80 → 0.60으로
  떨어졌습니다. 정답이 큰 덩어리에 섞이면 초점이 흐려집니다.
- **감점이 제외가 아닌 이유.** 스타일시트가 정답인 질문도 있습니다. 검색 단계에서 하는 것은 값을 바꿀 때
  재색인이 필요 없어서이고, 후보를 5배로 넓게 가져오는 것은 상위 8개만 가져와 감점하면 밀려서 못 들어온
  진짜 근거가 영영 안 보이기 때문입니다.
- **임베딩 모델.** 코드 기본값은 `jina-embeddings-v2-base-code`(768)이지만 `Back/Dockerfile`과 운영 설정은
  `multilingual-e5-large`의 int8 양자화판(1024)을 씁니다. jina는 한국어를 지원하지 않았고, int8은 같은 품질에
  2.52배 빨랐습니다. 모델이 다르면 차원이 같아도 테이블을 나눕니다. 섞이면 오류 없이 거리만 틀어집니다.
- **활성 빌드 안에서만 검색합니다.** 재색인 중에 새 빌드의 절반짜리 청크가 섞이면 아직 임베딩하지 않은
  코드가 "없는 코드"처럼 보입니다. 빌드는 쌓고 포인터만 옮기므로 재색인이 실패해도 옛 색인으로 계속 답합니다.
- **청킹 규칙은 해시로 식별합니다.** 청킹 상수와 함수의 AST, 임베딩 모델 이름, 접두어, 배치 크기에서
  sha256 앞 8자를 만들어 색인에 저장합니다. 규칙이 바뀌면 기동 시 낡은 색인을 로그로 알리고 재색인은
  관리자가 시작합니다. 자동으로 돌리면 배포 직후 모든 저장소가 한꺼번에 임베딩을 시작합니다.
- **검색 스니펫 본문에는 줄 번호가 없습니다.** 청크가 떨어진 조각을 이어 붙이는 과정에서 원본과 줄 수가
  어긋나는 경우가 48.8%였습니다. 헤더에 행 범위만 주고 정확한 행은 `read_file`로 읽게 합니다.

## 5. 인용 처리

세 단계입니다.

1. **프롬프트가 형식을 요구합니다.** 코드를 근거로 답할 때 어느 파일 몇 행인지 밝히고, 줄 번호가 붙어 온
   코드는 그 번호를 그대로 읽고 직접 세지 말라고 합니다. 검색 조각은 헤더의 범위만 인용하고 확실하지
   않으면 행 번호 없이 이름으로만 쓰라고 합니다.
2. **백엔드가 답변에서 인용을 뽑습니다.** `services/citations.py`가 유일한 파서이고, 화면 링크와 행 번호
   정확도 평가가 같은 함수를 씁니다. 파서가 둘이면 "채점하는 인용"과 "화면에 뜨는 인용"이 다른 집합이 됩니다.
   `41~100행`, `35행` 같은 행 표기를 잡고, 그 줄의 파일은 스냅샷에 보관된 소스 경로 목록으로 실제로 풀리는
   것을 우선해 고릅니다. 경로 매칭은 `/` 경계에서 끊고, 같은 이름이 둘 이상 맞으면 링크를 만들지 않습니다.
3. **화면이 링크를 걸고 코드를 펼칩니다.** 백엔드가 준 답변 안 위치와 실제 글자로 마크다운 렌더 트리의 노드를
   찾아 클릭 가능하게 바꿉니다. 클릭하면 인용 범위 앞뒤 20행을 붙여 보여줍니다.

**서버는 인용이 맞았는지 판정하지 않습니다.** 행 번호 실측 정확도가 71.1%인데 그대로 넘깁니다. 틀린 것을
감추면 고칠 수가 없습니다. 파일 밖을 가리켜도 요청 범위를 그대로 돌려줘 틀린 것이 눈에 띄게 합니다.
경로 해석이 보관 목록에 기대므로 보관 소스가 없는 스냅샷에서는 링크가 아예 생기지 않고, 죽은 링크가
구조적으로 나오지 않습니다.

## 6. 캐시와 데이터 저장

**프롬프트 캐시.** 대화 메시지는 아래 순서이고 캐시 브레이크포인트는 둘입니다.

```
system    : 대화 시스템 프롬프트                         ← cache_control
user      : 스냅샷 컨텍스트 원문 [+ 소스 번들]            ← cache_control
assistant : 요약
...최근 대화 20개...
user      : 질문   (도구 왕복은 이 뒤에 쌓인다)
```

검색 결과를 질문에 미리 붙이지 않는 이유가 여기 있습니다. 그 자리는 캐시 지점 뒤라 왕복마다 정가로 다시
청구되어, 실측 산식으로 3회 왕복에 기준선의 3.78배가 됩니다. 도구만 쓰면 2.11배입니다. 소스 번들은 반대로
스냅샷마다 고정이라 캐시 지점 안에 넣습니다. 도구 목록은 스냅샷 속성으로만 갈리고 한 대화 안에서 바뀌지
않으므로 접두사가 요청마다 흔들리지 않습니다.

`tool_result`는 대화 이력에 저장하지 않습니다. 이력을 개수로 자르는 구조에서 짝을 잃은 `tool_use`가 생기면
API가 거부합니다. 한 질문이 API 호출 여럿이 되므로 토큰·비용은 합산해 한 행으로 기록하고 왕복 수를 함께
남깁니다.

**데이터.**

| 테이블 | 내용 |
|---|---|
| `repos`, `repo_snapshots` | 저장소와 `pushed_at` 시점별 스냅샷. 컨텍스트 원문, 요약, 전체 주입이면 소스 번들 |
| `snapshot_source_files` | 스냅샷 단위 소스 원문. 도구와 인용이 여기서 읽음. 20MB를 넘으면 한 행도 보관하지 않음 |
| `chat_sessions`, `messages` | 대화. `snapshot_id`로 보는 코드 버전이 고정되고 `user_id`로 소유자가 정해짐 |
| `index_builds`, `code_chunks*` | 색인 빌드 상태·활성 포인터와 청크·임베딩. 모델별로 테이블을 나눔 |
| `runs` | 호출별 토큰·비용·시간·왕복 수. 관리자 페이지가 읽음 |
| `rate_limit_*`, `users`, `logins` | 남용 방지 카운터, 로그인 |

청크를 저장소가 아니라 스냅샷에 매다는 이유는 대화가 보는 코드 버전이 세션에 고정돼 있기 때문입니다.
저장소가 갱신돼 새 스냅샷이 생겨도 진행 중인 대화는 자기가 색인한 코드를 계속 봅니다. 소스 원문을 따로
보관하는 이유는 청크를 이어붙여 복원할 수 없기 때문입니다. 실측에서 비어있지 않은 줄의 8.5~12.7%가 어느
청크에도 없었습니다. 일부만 보관하지 않는 이유는 "없다"는 답이 저장소에 없는 것인지 잘려서 없는 것인지
구분되지 않기 때문입니다.

## 7. 설계 판단

- **근거 없는 답을 막는 장치는 세 겹입니다.** 프롬프트가 거절 문구 두 개와 "저장소에 없다 ≠ 수집 범위에
  없다"를 못박고, 보관 소스가 없는 스냅샷에는 `read_file`·`grep`을 아예 주지 않고(빈손으로 "없습니다"를
  돌려주면 모델이 그것을 "저장소에 없다"로 읽습니다), 잘린 결과에는 잘렸다고 적습니다. 모델이 텍스트 없이
  끝낸 응답은 정해진 대체 문구로 바꿔 빈 답변이 밖으로 나가지 않게 합니다.
- **인가는 한 곳입니다.** `/chat`의 네 경로가 전부 같은 함수를 거칩니다. 소유자가 없는 대화는 세션 id를 가진
  누구나 보고, 있으면 그 사람만 봅니다. 남의 것은 403이 아니라 404입니다. 없는 것과 남의 것을 구분해 줄
  이유가 없습니다.
- **남용 방지는 IP → 서비스 전체 → 사용자 순서의 세 층입니다.** 서비스 전체 일일 상한은 공평성 장치가 아니라
  비용 천장이라 사용자 수와 무관합니다. 캐시 히트에는 어느 층도 걸지 않고, DB 장애 시에는 통과시킵니다.
  상한은 비용을 지키는 장치이지 서비스의 관문이 아닙니다.
- **로그인은 신원 확인만 합니다.** GitHub OAuth에서 scope를 요청하지 않고 토큰을 저장하지 않습니다.
  저장소는 서버 토큰으로 읽으므로 비공개 저장소는 지원하지 않습니다. 배경 색인이 요청이 끝난 뒤 GitHub을
  다시 부르기 때문에 사용자 토큰으로 읽으려면 보관해야 하고, 그러면 비공개 코드가 서버에 쌓이기 시작합니다.
- **부가 기능의 실패가 본 기능을 막지 않습니다.** 정적분석, 색인 시작, 인용 경로 조회, 대화 저장이 실패해도
  요약과 답변은 나갑니다. 예외는 대화의 DB 장애(503)뿐입니다. 대신할 방법이 없습니다.

**측정 뒤 되돌린 것.** 최종 구조를 이해하는 데 필요한 것만 적습니다.

| 시도 | 되돌린 이유 |
|---|---|
| 검색 결과 사전 주입 + 도구 (하이브리드) | 스니펫이 캐시 뒤에 있어 왕복마다 재청구. 순수 도구보다 비쌈 |
| 청크 2,400자 | Python/JS에서 한국어 Recall@8 0.80 → 0.60 |
| 검색 스니펫에 줄 번호 | 청크 48.8%가 원본과 줄 수부터 어긋남 |
| 임베딩 배치 1 (마이크로벤치 2.2배) | 실제 재색인 3회에서 결론이 3번 뒤집힘. 원인은 CPU 점유 |
| Java 클래스명 → 파일 매핑으로 인용 파일 추정 | 관례는 72/72였지만 실제 답변에서 틀린 링크가 나옴 |
| 도메인 용어 사전을 검색어에 자동 부착 | 못 찾던 2개 개선, 잘 찾던 4개 악화 |

## 8. 현재 구조의 제한사항

- **단일 프로세스 전제.** 색인 큐가 메모리에 있어 `uvicorn --workers 2` 이상이면 워커마다 다른 큐를 갖고,
  남용 방지의 파일 폴백도 워커마다 따로입니다.
- **비공개 저장소를 지원하지 않습니다.** 위 로그인 설계의 결과입니다.
- **청크 300개를 넘는 저장소는 코드 검색이 없습니다.** 요약과 파일 목록으로만 답합니다.
- **색인 큐에 주인이 없습니다.** 사용자별 대기 상한이나 순서 조정이 없어 먼저 들어온 큰 저장소가 뒤의 모든
  색인을 세웁니다. 지금은 한 건당 청크 상한이 이것을 누르고 있습니다.
- **`/admin`에 인증이 없습니다.** 네트워크 경계가 인증을 대신하고, 외부에 열려면 인증을 먼저 붙여야 합니다.
- **인용 파서는 한 줄에 파일이 여럿이면 하나만 고릅니다.** "A.java 46행, B.java 55행" 형태에서 나머지가
  틀립니다.
- **소스 보관 이전에 만든 색인은 `search_code`만 받습니다.** `read_file`·`grep`이 빠진 이 경로는 측정된
  적이 없고, 해소는 재색인입니다.
- **배포는 `--force-recreate`까지 붙여야 반영됩니다.** `--build`만 하면 옛 컨테이너가 계속 돌 수 있고 빌드
  로그와 healthcheck가 둘 다 정상이라 알아챌 신호가 없습니다.
